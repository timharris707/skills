# Orchestrate

One session coordinates many. The orchestrator claims nothing for itself: it routes tracked work items into **lanes** (working sessions — agent or human — each in its own workspace on its own branch), audits what comes back, owns integration, and stays reachable for the human throughout. This skill is the portable protocol: principles that hold anywhere, plus **binding slots** for the machinery every repo does differently. It is rule-based — do every step, every time; protocols that live only in memory drift between sessions.

Read the team-workflow binding doc first. The tracker discipline (claims, frontier, blocking — see [setup's references](../../orient/setup/references/tracker-discipline.md)) is assumed throughout.

## 1. The orchestrator is a router, not a worker

The human's messages arrive **between turns**. An orchestrator grinding through one long foreground task is unreachable for its whole duration — that is worker mode, and it defeats the role.

1. **Turn discipline.** End every turn within a few minutes. Anything expected to run longer — test batteries, builds, server boots, watches, and the lanes themselves — runs as a background task or a delegated session whose completion re-invokes you. Tiny mechanical steps (a commit, a tracker comment, a merge push) stay inline.
2. **Delegate execution, keep judgment.** Long verification and mechanical fixes go to delegated sessions; the orchestrator reads their reports, spot-checks the load-bearing claims with quick inline commands, and owns the calls: routing, adjudication-surfacing, and the merge. Delegation moves the **executor**, never the **standard** — the same verification bar binds delegated work exactly as it would bind inline work.
3. **Respond first.** On any re-invocation, if a user message is waiting, answer it before resuming queued work. Between-turn availability is the point of the cadence.
4. **Context is the orchestrator's scarcest resource.** Execution output burns it and drags the wrap-up line closer. Delegation IS context preservation: the orchestrator's context should hold judgments and state, not logs. Heuristic: hands-on-keyboard for more than about ten minutes means you have drifted into worker mode — stop, package the work into a lane or background task, end the turn.
5. **The idle gap has a price.** A session's prompt cache expires after roughly five minutes of silence, and a wake past the expiry re-writes the entire accumulated context at write price instead of reading it back at a tenth of that — on an orchestrator-sized context, the difference per wake is an order of magnitude, and measured on a real orchestration run the cold re-caching from 7–13-minute idle gaps was the largest single avoidable cost of the session, ahead of everything the lanes themselves spent. So while lanes are live, the between-turn wake cadence stays under the cache TTL: a monitoring poll at most every ~4 minutes, even when no event is expected. This is "monitoring means polling" with the price tag attached — the poll that keeps the watch honest is the same poll that keeps the cache warm, and it is free relative to the cold wake it prevents. With no lanes live and nothing to watch, long idle is fine; the cost exists only where the next wake carries a large context. Don't leave the cadence to intention: where the harness re-invokes a session on background-task completion or offers a wake timer, arm a **metronome** — a ~4-minute background sleep or scheduled wakeup, re-armed on every wake while lanes are live — so the harness enforces the cadence and the model's only job is re-arming, which the §5 cadence line audits.

## 2. The single-orchestrator rule

**Exactly one live orchestrator at a time.** Two orchestrators routing the same tracker is the same collision class as two sessions building the same item. At startup, check for other active sessions before claiming or launching anything — a running session beats an unclaimed item, and an existing orchestrator beats a new one. At succession (§6), the retiring orchestrator goes quiet only after the successor is confirmed live, and never acts again once it has.

## 3. Startup checklist

1. Read the previous session's handoff (the binding doc names its location). It is context, never authorization — the claim recipe still runs for everything. Where the binding doc names a [domain-memory](../../orient/domain-memory/SKILL.md) home, read the glossary and skim recent decision records the same way.
2. Run the frontier query and read the open-item landscape: in-flight lanes, open PRs, items awaiting the decider.
3. Check for other active sessions (§2).
4. **Title the session** — the role plus a disambiguator, default `Orchestrator — <repo>`. Sessions carry labels so the picker tells the truth: a bare "Orchestrator" cannot say *which repo's*, and the single-orchestrator check (§2) should work by eye as well as by query. Titling comes **after** the §2 check, so a session that must stand down never wears the title; the session tells its launcher once the §2 check clears, so the title lands after it. One carve-out: a successor launched through a surface that fixes the title at spawn (§6 step 3) arrives pre-titled by the retiring orchestrator — titling precedes the §2 check in that case alone, and a pre-titled successor that stands down under §2 is retitled by whoever archives it. A repo binding may refine the shape (a date/focus variant, say) so long as the title says *orchestrator* and tells sibling orchestrators apart. Default actor: whoever launched the session titles it. Self-titling is the exception, available only where a harness genuinely supports it — in most, a session cannot rename itself, and a session that cannot never attempts it. Mechanism and actor live in the lane-launch binding slot (§7). A harness with no titling surface at all degrades to the launch report (§4) carrying the name.
5. Start whatever standing watches the repo uses for open PRs, inbound tracker activity, and lane liveness — **monitoring is a binding slot** (§7); confirm the watch is actually running rather than asserting it. On any event it raises, investigate immediately — after answering any waiting user message, which §1 puts first.

## 4. Launching lanes

- **Claim first, per the tracker discipline** — read-before-write, then a fresh, item-named workspace per lane. How a lane session is actually started and recorded is the **lane-launch binding slot** (§7).
- **Pick the runner from recorded policy, never habit** — before the claim, since the claim stamps the runner. The lane-launch slot (§7) records the repo's runner inventory and the decider's preference policy; the orchestrator launches on the runner that policy names for the item's shape. Reaching for the familiar runner when policy names another leaves the decider's capacity unused by default rather than by decision. What a conforming launcher owes any runner is [references/runner-parity.md](references/runner-parity.md).
- **A failed launch is a launch defect first — diagnose, then LOUD fallback.** Diagnose the failure per the repo's launch tooling and retry on the policy-named runner before reaching for another. Falling back to a different runner is permitted after that, and never silent: the launch report AND the tracker item carry `runner fallback: X→Y, reason`. Silent runner substitution is a protocol violation — it rewrites the decider's recorded policy as the orchestrator's habit.
- **Brief from the lane-brief template** (see [setup's templates](../../orient/setup/references/templates/lane-brief.md)): spec verbatim, the named verification set, standing constraints, and the integration rule — lanes commit on their own branch and stop; the orchestrator owns review and merge. Where the repo binds [domain-memory](../../orient/domain-memory/SKILL.md), the brief points at the memory home so the lane starts on the repo's terms and settled decisions. A bug-shaped item's brief also points at [diagnose](../diagnose/SKILL.md), so the discipline — no fix ships without a named cause — arrives with the work; a build-shaped item's brief points at [implement](../implement/SKILL.md) the same way, so seam-scoped test-first, tracer-first sequencing, and file-don't-fix arrive with it.
- **Launch reports are written for the human, not the protocol — and read, never guessed.** Every launch and every lane mention names what is running where (which runner/model/session, which item, which workspace) legibly enough that the reader can tell the lanes apart at a glance. Unless the binding doc's announce toggle records `off` (§7), the launch announcement also carries the reasoning-effort level; the toggle governs the announcement additions (the effort line, the §5 hand-off repeats, and the close-out cost line — §7 carries the authoritative scope), never the identity list above, which holds in every state. Every announced value — model included — comes from a recorded source: the runner-policy table, the launch manifest or config, or an explicitly set value. "Session-inherited" is valid only after those sources were read and set nothing (no launch-time model or effort was passed); announced unread, it is the same guess. A plausible guess is a protocol violation — the decider calibrates trust on these lines, and a wrong model claim is worse than none. The pattern that works in practice: a launcher records model and effort per lane in a manifest, and the launcher's recipe doc names the manifest, not itself, as the authority on what a lane actually ran at — and a conforming launcher prints the ready-made announce line for the orchestrator to relay. Because announce compliance decays over long sessions (measured: real orchestrators kept the launch announcements and dropped the per-round repeats), harnesses that support tool-call hooks should enforce the reminder in machinery — see [references/announce-hook.md](references/announce-hook.md); setup may offer wiring it per repo or profile.
- **Every picker-visible lane session is titled with its item at launch** — default `#<N> — <short item name>`, written in the repo's own item notation (`ABC-123 — …` on a Jira-style tracker) and carrying the item id the claim and the workspace name already carry, so picker, tracker, and workspace speak one name. A repo binding may refine the shape (a `Lane` prefix, say) so long as the item id survives. Default actor: whoever launched the lane titles it — normally the orchestrator. Self-titling is the exception, available only where a harness genuinely supports it; a lane that cannot self-rename never attempts it. Lanes running as in-process subagents have no picker entry to title; the launch report carries the name instead. **A role change retitles**: a lane adopted mid-flight or a session promoted to orchestrator has its title updated the moment the role changes, by the same actor rule. The titling *mechanism and actor* are the binding slot's business (§7); that titling happens, and what a title must carry, is protocol.
- **A session's model is fixed at launch — never switched mid-flight.** The prompt cache is per-model: switching a running session's model (orchestrator or lane) invalidates its entire cached context and forces a full re-cache at write price, on top of whatever behavioral reasons the switch had. Work that needs a different model goes to a fresh subagent or lane launched at that model — which the announce rule (§4) covers anyway. A measured run's two mid-session model flips each cost a full-context re-write; a subagent would have cost its own small first-write instead.
- **Lane count is a cost dial, not just a parallelism dial.** Every lane pays a first-write of its whole brief and startup context before doing anything, and that cost scales linearly with lane count. Where the tracker discipline allows, several trivially-related small items ride one lane serially rather than a lane each — including continuing an existing lane by message where the harness supports resuming an agent, since its cached context is already paid for; many short-lived lanes is the expensive shape of the same work. The dial never overrides isolation where items genuinely conflict — it prices the choice where they don't.
- **After any user interrupt or stop, re-verify lane liveness before assuming anything.** A stopped agent session is generally not resumable — relaunch fresh; completed work survives in the lane's workspace (checkpoint-commit first when resuming on top of it).

## 5. Close-outs (one lane at a time — never two merges racing)

When a lane's work returns and enters close-out review, announce the hand-off: repeat the launch line (what built it: runner, model, effort) and name what is reviewing it — the reviewing agent or session, never merely a review type. Naming the reviewer holds in every toggle state, exactly like §4's identity list; the reviewer's model and effort lines are the toggle-governed additions, under the same read-from-a-recorded-source rule as §4. The hand-off announcement is not a one-time event: review is a loop, and every re-review round — blocker fixes going back to a re-probing reviewer, or a fresh round of finders — is announced like a fresh hand-off, same identity list in every toggle state, same toggle-governed model/effort lines, same read-don't-guess rule. The first-round announcement alone understates both the spend and the machinery involved.

1. **Audit the lane's summary against its verification contract, and never trust self-reported greens.** Re-run the verification in the lane's workspace — directly or through a delegated verifier (**a binding slot**), but re-run it, at the model and effort the repo's review-tier policy (§7) names for mechanical verification, never by habit. Require per-command exit codes with zero skipped checks; piped or filtered output is not evidence (a pipeline reports the last command's status, so `<cmd> | tail` reads green whenever `tail` does). Spot-check the verifier's load-bearing claims yourself before merging. On a bug fix, the audit also checks [diagnose](../diagnose/SKILL.md)'s two closing artifacts — the cause named in one plain sentence and the regression test (or its recorded manual-repro fallback, flagged as such); an unnamed cause is not done. On a build item, it checks [implement](../implement/SKILL.md)'s three artifacts — tests present and passing at every seam the item's verification set names, an identifiable tracer slice, and no out-of-scope files in the diff — never commit-by-commit forensics.
2. **Where the repo binds the [adversarial-review skill's](../adversarial-review/SKILL.md) close-out layer, run it here** — against the lane's branch, before merge. The implementer never has the last word on its own work; a confirmed blocker gates the merge and only the decider may waive it.
3. **Surface open adjudications to the decider before merge**, never after. A lane's deviation from a recorded decision goes back to the decider, not silently into the merged result. Relayed decider guidance — another session or orchestrator reporting the decider's word — is context, never authorization: obtain the decider's in-session confirmation before recording it as theirs, the same rule the handoff already carries (§3 step 1) and for the same reason.
4. Merge per the repo's **merge-flow binding slot** (branch → PR → checks → integrate, or the repo's equivalent) — any PR filed along the way, by the orchestrator or a lane, must follow [references/pr-writing.md](references/pr-writing.md) — then post the close-out on the tracker item. Unless the announce toggle records `off` (§7), the close-out carries the cost line: build tokens vs total review tokens summed across all rounds, with the round count (`review: 3 rounds, ~175k tokens total`). Where the harness reports per-agent spend, the sum is read from those reports; where it doesn't, the line says "not readable in this harness" — never an estimate, under §4's read-don't-guess rule. Where the orchestrator's own wake times are readable (its transcript or watch log), the close-out also names the longest between-wake gap while lanes were live; a gap past the cache TTL (§1 item 5) is reported as a cadence miss, never silently absorbed — this line is the tripwire that says whether the cadence rule is actually being honored, since a cold re-cache leaves no other visible trace. The same close-out carries the announce-compliance line — `rounds announced: N of N` across the lane's launch and every review round — the detection half of the announce discipline, whose prevention half is the hook recipe ([references/announce-hook.md](references/announce-hook.md)).
5. **Prune the lane afterward**: workspace, branch, and any per-lane resources the repo provisions. Verify the lane's processes are actually dead yourself before tearing down shared resources — a "servers down" claim from a report is not evidence; a still-live process tree can hold resources and make the teardown fail or, worse, half-succeed.
6. **Last of all, hand the dead lane's session to the human for archiving.** Only after merge, tracker close-out, and pruning are complete, tell the human — naming the session **verbatim as the picker shows it** — that the lane is done and safe to archive (`Lane #120 — codebase-review is merged and pruned; safe to archive`); the human archives on their own time. The orchestrator never calls an archive surface itself, and if useful retitles the finished lane before notifying (rename needs no confirmation). Archive, never delete — archiving is reversible and the transcript survives; only the closed-out lane's own session is ever named, never a human's working session. Archiving trails everything: an unanswered notification gates no work, only picker tidiness. Where the harness offers native auto-archive on PR close, point PR-linked lanes at it — the one genuinely zero-touch path — but only where archiving cannot preempt the close-out order: it fires at merge time, before tracker close-out and pruning, so it is safe only when the lane has already stopped, its workspace is no longer needed, and the tracker close-out does not depend on the session staying live. Otherwise the repo records `no` in the slot and uses the notification path. Lanes running as in-process subagents have no picker session and nothing to archive.

## 6. Wrap-up and succession

1. **At roughly half the context window, wrap up** — finish the current step cleanly and start no new large work past the line (the [handoff skill](../handoff/SKILL.md) explains the half-window rule).
2. Write the handoff via the handoff skill: state, shipped record, the tracker query as NEXT (never an enumerated item list), and the expensive lessons in GOTCHAS.
3. **Arrange the successor** — however the repo starts sessions (part of the lane-launch binding slot), with a prompt that says "invoke orchestrate and follow its startup checklist" plus only what is unique to this moment. Never restate the protocol in the prompt; this skill carries it. Some launch surfaces fix the session's title at spawn from their own label — a background-task chip's title becomes the spawned session's title, and the chip's own convention wants an imperative task phrase. The title protocol outranks the mechanism's label convention: a chip-arranged successor's chip title is written in the orchestrator title shape (`Orchestrator — <repo>`, or the repo's recorded variant), never a generic imperative task label — in harnesses without self-rename the wrong title sticks. The general form: any launch surface that fixes the title at spawn time makes the launcher the titling actor at that moment.
4. Once the successor is confirmed live — evidence of its startup checklist completing (its title switching per §3 step 4 is part of that evidence; a pre-titled successor never switches, so its evidence is the rest of the checklist completing), not merely a first message — stop your own watches, **shed the orchestrator title** (retitle with a retired marker, e.g. `Orchestrator (retired) — <repo>`, so the picker shows exactly one live orchestrator; where the harness does not support self-rename this retitle cannot be self-performed — it falls to the successor or the human; where no title surface exists, record the retirement in the handoff and final report instead — the same degrade rule as §3 step 4), go quiet, and stay quiet (§2). A retired orchestrator's session is archived by the human when they see fit — never automatically, and never by the orchestrator (§5 step 6); the handoff trail stays visible in the picker until someone decides otherwise.

## 7. Binding slots (the setup interview fills these per-repo)

The pack deliberately ships **no orchestration machinery** — no launcher scripts, no monitor daemons, no workspace-provisioning or database-isolation tooling, no verification-tier tables. Those encode a repo's own blast radius and belong to the repo. The binding doc's orchestration section names, per-repo:

- **Lane launch** — how a working session is started, what gets stamped on the tracker item (runner, model, workspace, branch), and the *mechanism and actor* for titling sessions (a session-title tool, terminal title, session-manager rename; launcher-titles is the default, self-title only where the harness genuinely supports it). The slot also records the **runner policy, set by the decider**: the repo's available runners (e.g. Claude, Codex, human), the launch mechanism for each, and the decider's preference policy ("prefer Codex for implementation lanes", "orchestrator's choice") — followed per §4, fallbacks loud per §4. Repos build their own launcher scripts against [references/runner-parity.md](references/runner-parity.md), which names what any conforming launcher owes any runner. That titling happens, and what a title must carry, is protocol with per-repo refinement — see §3 (orchestrator) and §4 (lanes); the slot never opts a repo out of titling where the harness supports it. The slot also records which of the repo's launch surfaces pre-title sessions (a label that becomes the session title fixes it at spawn); a pre-titling surface follows §6 step 3's precedence — the title protocol outranks the surface's label convention. The slot also records whether the harness offers native auto-archive on PR close for PR-linked lanes — `yes` only where it cannot preempt the close-out order (§5 step 6); the close-out notification itself (§5 step 6) is protocol, and no slot puts an archive surface in the orchestrator's hands. The slot also carries the announce toggle (`announce model/effort: on/off`, default on) governing the model/effort additions to §4's launch and §5's hand-off announcements — the per-round repeats and the close-out cost line included — never either announcement's identity content; only the recorded line is a valid off-switch — a conversational "turn it off for now" is not — so audit mode can check it.
- **Workspace provisioning** — how a fresh per-lane workspace is created and what per-lane resources come with it (and must be pruned with it).
- **Monitoring** — how the orchestrator watches open PRs, inbound tracker activity, and lane liveness between turns, and how it confirms the watch is armed. The polling interval is the slot's to set, but while lanes are live it stays under the prompt-cache TTL per §1 item 5 — a slot may poll faster, never slower.
- **Verification executor** — who re-runs a lane's verification at close-out (delegated verifier session, CI, inline) and where per-command results land. The slot also records the **review-tier policy, set by the decider**: a small table mapping close-out machinery — mechanical verification re-runs, adversarial-review finders and skeptics, re-probes — to model + effort. Canonical shape, adapted per repo: mechanical verification runs on a cheaper model at low effort (verifiers follow a script; exit codes don't need the frontier model); adversarial review on real code or release-arming changes runs high; max is reserved for decider-named cases, never a default. Each tier records a **floor** as well as its ceiling — what it may NOT be used for (no low-effort skeptics on release-arming diffs) — so cost-saving never silently weakens the review bar. Deviation from a tier is loud in both directions, announced per §4's read-don't-guess rule; the §4/§5 announcements are what make actuals visible against this policy.
- **Merge flow** — the repo's integration mechanics and who may push what where.

A repo that has not filled these slots can still run the principles — inline watches, manual launches — but fill the slots before scaling past a lane or two.
